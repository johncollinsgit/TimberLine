# Department request type and intake priority

This source candidate extends the signed-in department request form and native `RequestWorkflow` commands. It does not seed a runtime, change membership or activate an integration. The existing encrypted request JSON stores the two optional fields; no migration or legacy backfill is required.

`request.create` accepts `request_type` (`general`, `it_support`, `event_setup`, `plumbing`, `lighting`, `maintenance`) and `priority` (`low`, `normal`, `high`, `urgent`). Omitted legacy fields remain absent and display **Not recorded**; null explicitly records no value. No title, requester category or description is used to infer either field. HTTP validation and the native command service both reject unknown values, arrays and the ambiguous `type` alias.

A current department coordinator may use `request.classify` before assignment, with the existing positive expected revision and exact request receipt key. That command changes only supplied classification fields, under the existing tenant lock, encrypted audit and version increment. Current coordinator authority is rechecked before an accepted receipt can be recovered. Editors/requesters cannot classify; foreign area/runtime/tenant IDs do not broaden access. Assigned requests must use the existing task controls to change priority.

Assignment explicitly passes the recorded intake priority to native task creation. A legacy request without one retains the native **normal** assignment default. The DTO's `requested_priority` remains the original intake, while `priority` and `priority_source` reflect the currently authorized native task after assignment. Native task priority changes do not rewrite the saved intake or request revision. Table sorting and linked Buildings open/urgent summaries use that effective priority; only explicit authorized saved-building links contribute counts. A text match stays separate and unverified.

The form exposes these controls only for the private version-1 `request_fields` contract. The isolated public sample and older transports omit them. Request detail and Buildings detail show the available type and priority source. Coordinator classification shares the existing uncertain-outcome retry control and retains the exact command ID/body; saving classification preserves a separate unsent note draft, and saving a note preserves unsaved classification choices. Close/Escape and reload retain existing scoped draft behavior.

The separate **published RequesterPortal** is unchanged: its category is not the new type, and that intake neither persists nor displays these fields. Department coordinators can subsequently classify such an unassigned request. No universal requester-form support is claimed.

The Requests tour explains intake versus task priority and the currently available coordinator action. It does not submit, assign or generate work. Source changes alter the review-source edition; deployment and any review-link publication require the normal exact-commit/check/review procedure. A source-only demonstration or local fake HTTP is not live runtime acceptance.

Run `php vendor/bin/phpunit -c phpunit.enterprise.xml` and the existing Enterprise CI Node command. `EnterpriseRequestClassificationTest.php` is explicitly registered and exercises real isolated routes, persistence, encrypted history, legacy/portal boundaries, finite validation, revoked permissions, exact retries and native task-priority handoff. Local headless fixtures use fictional records and mocked HTTP only; they separately exercise native form controls, exact retries, scoped drafts, reload rendering and Requests tour copy in Chromium/WebKit at desktop, iPad and mobile sizes. Production seed/scheduling remains separately held for fresh inventory, topology and a reviewed exact plan.
