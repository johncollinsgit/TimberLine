## Fixed loss paths

The shared web task reset previously cleared unsent notes/comment input on search, filters, task/subtask links and related navigation. Comment retries also generated a new key/comment ID, risking a second comment after a lost committed response. A successful comment refresh could replace separate unsaved task edits. A save-confirmed response followed by an access-refused refresh needs different handling from an unconfirmed save.

The existing Blade/plain-JavaScript app now keeps one active unsaved task context and creation/comment editor context in **page memory**. It blocks destructive navigation until the user saves or explicitly discards the pending edits. It does not introduce a second task store, a browser-storage cache or a native app. A visible retained-work bar explains the state and offers resume and explicit unsent discard; saved source/history/files are never discarded by that control.

| Surface | Behavior and actual evidence |
| --- | --- |
| Search/filter/project/view changes | Revert the changed control to its accepted value; preserve task fields and comments instead of clearing the detail. |
| Task/subtask/related links, in-app Back, new task, project settings/templates and workspace entry | Refuse navigation while protected task input or a save remains unresolved. The existing workspace/planning/status guards remain in force. |
| Detail keep-and-close | Hide details while retaining the active input; explicit resume verifies original identity and current edit access before restoring it. It does not create multiple navigable draft documents. |
| Creation/comment-edit Close, Cancel or Escape | Keep typed values in the page; reopen/resume the same creation identity or comment draft. A blank untouched creation can be abandoned without a write. |
| Ordinary links and Livewire navigation | Intercept while protected work is unsaved; require save or explicit discard first. |
| Browser Back, Forward and window Close | Register the native beforeunload warning; actual Chromium cancellation preserves the page/input. Clean traversal reauthorizes. If the user chooses Leave or the browser suppresses warnings, memory cannot survive document destruction. |
| Restored document | A restored-page event seals retained input and requests verification instead of blindly reloading it away. The restored-event drill is synthetic; native/mobile lifecycle certification is separate. |
| Repeated save/recovery/discard clicks | Serialize the operation, freeze editing during pending/verification, and disable dependent controls through the whole save/refresh. The browser regression found an early-enabled subtask control; it now remains disabled until refresh finishes. |

Protected task input includes title, description, assignment, start/due date, priority, new comment/mention, own-comment edits, quick-create selections, visible structured field values and recurrence settings. Missing assignee/mention/section options are retained as unavailable placeholders rather than silently changing a draft to empty/unassigned. A missing field or lost project/parent edit permission prevents restoration rather than silently dropping its value.

Project settings/template builders and existing project-status/follow-up drafts retain their separate, previously documented scopes; this is not a universal draft system for every configuration form. ## Save confirmation and conflict rules

Task edits, quick creation, add/edit comment, structured values and recurrence use a frozen command payload, existing UUID idempotency key and, where relevant, fixed task/comment ID. Repeated clicks during a request issue one command. An unknown network/server outcome freezes that exact request for explicit retry; no new key or automatic replay is created. Six committed-response-abort drills confirm exact key/payload identity and no duplicate logical write. A 503 drill also preserves an unconfirmed request. The server's existing receipts reauthorize current work and return current projections; no receipt bypass or new schema is added.

Known validation refusals retain editable input. A version conflict retains new text and requires explicit reload/review against the current authorized saved text, fields/recurrence and version before saving; both versions are not silently merged or overwritten. Confirmation of an earlier save does not reapply its old text over a newer saved description. If an uncertain comment is confirmed after another device changed a separately edited field, that field still requires explicit comparison before save. Confirmed writes followed by failed access refresh remain confirmed while separate unsent work stays sealed; the confirmed write is not queued again.

Native task revisions/events continue preserving saved changes. Comments, original descriptions/source provenance and attachment history are not rewritten by draft handling. No emails/push/real invitations/imports/provider calls occur in these fixtures.

## Account, workspace and permission boundary

`EnsureTeamWorkViewer` adds an optional stale-page refusal fence to the existing authenticated web and bearer Team route groups. Web requests send their page's expected viewer/workspace headers. A mismatch returns a content-free 403 with saved=false **before** controller reads/writes. Matching headers never grant access: existing current membership, module/rollout, tenant/object and bearer abilities remain authoritative. Existing API clients without the optional headers keep their existing server authorization. Successful responses carry the actual viewer/workspace header; the web client refuses mismatched projections and fences stale continuations with an access epoch.

On authentication/access refusal or a dirty page returning from hidden/focus/restoration, protected DOM content/options are cleared and drafts remain sealed in the page closure. Draft snapshots retain changed input and necessary IDs/version/request identity. An exact frozen request can also contain existing values included by the reviewed task form; it stays sealed under the same current-account/object rules. Full unchanged source records/history are not copied into a separate draft store. An edited description may contain source text, so recovery requires the original signed-in account **and current task edit access**. Creation recovery also verifies original project/parent access; structured values require their current field write context. A current account/workspace probe reuses the existing authenticated directory. After same-account sign-in, the response supplies the session's current CSRF token for the existing page; no token/credential/configuration is created or rotated by this feature.

An actual local cookie-account swap and stale-page write prove that the other account cannot read the retained draft through the UI or submit it as themselves. Actual project revocation hides drafts/originals until the same account regains edit access. An actual signed-out session refuses recovery until sign-in is restored. Retained content is never put into localStorage, sessionStorage, IndexedDB, history state, URLs, cross-user drafts, server draft records or telemetry. There is no scheduled replay, timed discard or purge.

Detection is driven by browser focus/visibility/restored events and authenticated responses. This is not a new cross-tab session broadcast or instantaneous remote revocation channel. A session change without any browser event/request cannot be detected instantly. Current server authorization still controls all reads/writes; full native/device cache and background/session acceptance remains open.
