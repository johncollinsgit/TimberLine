# Everbranch Simple self service purchase

This is Everbranch's platform subscription lane. It is separate from tenant-owned website checkout, Stripe Connect merchant onboarding, and legacy signed agreements. Existing agreements, old tier mappings, customer payment accounts, and provider-specific activation gates are preserved.

## New account and purchase

The public setup starts with photo cards for business templates. Each template resolves its included tools from the current safe public catalog; client module lists cannot override it. Template selection grants no access and starts no provider connection. The saved template continues to `/platform/signup` for email registration. New accounts are active but have no tenant or paid access until a current-account, signed email verification is completed. Passwords use the existing application rules and hashing. Email delivery failure preserves the account and exposes a throttled resend. Google first-time accounts use the same path; only an explicit verified provider claim for the matching stored address skips email verification. `EVERBRANCH_SELF_SERVICE_REGISTRATION_ENABLED` independently controls enrollment (default true); legacy account-request and existing tenant flows remain available.

After verification, the chosen template is shown once with the business-name form; it is not requested again. A missing template returns to the chooser. The template and business name create one provisional base workspace under a user lock. Included website addresses fit DNS label limits and avoid configured platform hosts. Only this fresh path assigns the owner membership and server cohort marker. The template and safe tool selection survive authentication and provisioning. The purchase page displays the canonical setup/monthly total and acceptance, with tool details collapsed; returning unpaid owners resume this page on login. The workspace guide retains a Your plan link. A URL return displays pending status until the server confirms actual paid evidence.

Only a verified active tenant owner in a newly provisioned cohort (`tenant_access_profiles.metadata.self_service_registration`) can buy. That registration marker grants no paid access. The canonical standard offer supplies setup, monthly cost, currency, included branches and usage disclosure. The review page accepts a server quote hash and current terms version before payment. The first charge is $499 setup plus $299 first month before provider-calculated tax; subsequent invoices charge the frozen $299 monthly amount.

Before the first provider request, a tenant-serialized intent stores the exact accepted quote, actor, acceptance timestamp/IP/user agent, platform account, test/live environment, checkout request and stable idempotency key in the existing commercial billing mapping. A corresponding existing fulfillment row records its lifecycle. It contains no API credentials. Existing signed billing orders retain their non-null agreement/version/acceptance requirements; self service never fabricates a signature or reuses an unrelated agreement.

Safe public included branches can be selected. Public dependencies are included automatically; hidden/internal connectors and mailboxes retain existing setup/provider controls and cannot be selected or activated through a crafted purchase. Paid owners can add more included branches without another payment. Explicit non-self-service entitlement overrides are retained.

## Provider readiness

- `EVERBRANCH_SELF_SERVICE_PURCHASE_ENABLED=true` enables this purchase lane.
- `EVERBRANCH_SELF_SERVICE_WEBHOOK_VERIFIED=true` is an operator assertion of actual signed callback acceptance; it is not paid evidence.
- Supply the platform `STRIPE_SECRET`, `STRIPE_ACCOUNT_ID` and `STRIPE_WEBHOOK_SECRET` server-side. Test and live accounts stay distinct; rotating a key within the original account/environment does not change the purchase identity.
- Before Checkout creation the app retrieves the authenticated Stripe account, confirms its frozen ID and charges capability, and checks Stripe Tax settings are active. Automatic tax is required. Checkout collects the billing address and displays the provider's final tax. The application does not decide a tax jurisdiction or tax obligation.
- API requests use Stripe version `2024-06-20`, ensuring the tested invoice/payment-intent fields remain stable. Checkout redirects are limited to HTTPS `checkout.stripe.com`.

The existing `/webhooks/stripe/events` endpoint verifies the raw body signature and timestamp before dispatching this lane. Configure Checkout completed/async payment success, invoice paid/payment succeeded/payment failed, subscription updated/deleted, charge refunded and dispute created/closed events. Real provider acceptance must validate the exact account/environment and endpoint signing secret; passing source tests or having a key alone does not establish live readiness.

## Confirmation and recovery

Manage billing opens Stripe's hosted portal for the original verified customer, account and environment. The server uses historical signed purchase evidence and an active owner membership; browser fields and legacy customer mappings cannot select another customer. New-purchase flags may remain paused while an existing owner reviews invoices or updates a payment method. Stripe portal configuration controls available subscription actions. An expired paid account is shown billing recovery rather than a second setup purchase.

A redirect, signup, arbitrary session ID, or copied paid flag never activates service. The server retrieves the original Checkout session, subscription, invoice and succeeded PaymentIntent in the original account. Purchase UUID, quote hash, tenant, environment, initial subtotal, currency, customer, monthly unit amount/interval/quantity, invoice association and actual received amount must match. Paid-out-of-band invoices, discounts, pending payments, connected-account events and mismatched references fail closed. Refund/dispute evidence prevents new grants. Renewal refunds and disputes resolve through authenticated charge/invoice/subscription/customer relationships; copied metadata cannot rebind another tenant. The signed receipt, immutable original paid receipt, subscription coverage and applied fulfillment jointly establish eligibility.

Checkout and webhook fulfillment use the same tenant lock. Duplicate webhooks reuse their receipt and fulfillment. A lost Checkout response retries the same frozen request/idempotency key within its safe window. Unknown outcomes are never replaced after that window. A known original session can be resumed; only an authenticated retrieval proving expired + unpaid + no subscription/invoice/payment intent permits archiving it and starting a new attempt. Old attempts remain in purchase history and cannot fulfill the replacement.

`billing:reconcile-self-service` retries retained signed receipts whose remote verification failed. It also refreshes expiring/past-due subscription coverage from retained original signed evidence and current authenticated provider reads, covering missed renewal callbacks. It creates no synthetic Stripe event and never initiates another charge. Schedule every five minutes with overlap protection; retain the original authorized platform credentials for recovery even if new purchases are paused.

`SelfServicePurchaseEligibility::paidForTenant()` is read-only and requires current active paid-period coverage. `hasVerifiedPurchase()` separately establishes historical verified purchase for preserving an already published snapshot. Expiry/cancellation stops new publishing while snapshots and records remain intact. Explicit canonical module restrictions and global publication freezes retain authority. A missing schema, copied registration flag or unconfirmed intent returns false.

## Acceptance

Scoped tests cover canonical prices, all public branch selections, hidden dependency exclusion, explicit terms, signed confirmation, account/mode isolation, manual/unpaid rejection, webhook replay, legacy preservation, branch additions without recharge, renewal/cancellation, expired-session replacement, lost-response idempotency and retained-receipt recovery. The cross-subsystem journey exercises actual signup routes, mailed signed verification, provisioning, checkout, signed webhook, real eligibility, publishing and public subdomain rendering with fictional Stripe responses. Before live launch also complete an actual provider test purchase, signed callback, receipt/subscription matching, workspace entitlement, publish and expiry/retry exercise. No source test should be reported as a real payment or a live published customer site.
