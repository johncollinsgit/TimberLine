## End-to-end local behavior

The project selector opens a responsive overview showing the original description, current owner label, existing start/due dates, privacy/archive state, manual status and completion counts. Counts include only currently readable tasks explicitly added to this project, each canonical task once; inherited-only subtasks and unreadable/private-parent work are excluded. There is no hidden/global total or inferred milestone/workload figure. Status `complete` does not complete tasks or archive a project. Native Field job/checklist/status/time behavior is unchanged.

Canonical project web links carry the explicit workspace and UUID, authorize before HTML, and restore the selected project/overview without signing out. Ambiguous simultaneous task/project targets are rejected. Copy-project-link uses the existing selectable readonly fallback; the actual PC clipboard was not changed by testing. Native/OS dispatch and other entity link families remain open.

The new `project.status` command uses the same tenant-locked WorkGraph/repository and current active/verified membership, canonical entitlement and rollout resolver. Only the current project owner with an eligible owner/admin/member tenant role may post. Guest/viewer/editor access alone does not confer posting rights. Posting requires the exact project version and explicit review of new text, references and audience. A privacy/ownership change refuses stale posting atomically. Archived projects remain readable but cannot post until reopened.

Manual states: on track, at risk, off track, on hold and complete. New summary (4,000-byte graph bound), highlights/blockers/next steps (2,000-byte bounds each) are independent plain text; null optional fields normalize to empty strings. Original project/task descriptions, comments, files, history and recurrence are not copied, summarized, rewritten or completed. Up to 20 task references require current read access, explicit membership in the target project and an exact task version. This is task-only reference support; milestones remain pending. References never grant access and their IDs/titles are projected against current permissions on every overview/history read.

No new table/migration or second work store exists. A project keeps only its current status record, with protected reference versions. Every actual post creates an immutable existing native project-version snapshot and a `project.status` event pointing to that exact version, in the same transaction as its receipt. Other project edits do not create duplicate status entries. History verifies each snapshot SHA-256 and entity/tenant/revision binding; missing/inconsistent evidence produces an explicit 503 rather than partial/unverified notes. Checksums do not constitute a signed or tamper-proof audit ledger.

History uses 10-update pages. Opaque encrypted cursors reuse the existing app encryption key and bind the viewer, project and tenant; no key/credential was created or rotated and global event IDs are not exposed. Current permissions are rechecked after history retrieval and references/counts are projected from fresh state. Pages replace prior displayed pages, with Latest/Older navigation. Closing an overview cancels its stale continuations. The directory carries only compact current-status metadata, not narrative/history bodies. The service remains based on the existing tenant graph; representative large-tenant query/index and MySQL performance/recovery acceptance is still required.

Identical UUID retries confirm one saved update and return its original posted identity even if a later update is current. A changed payload on the same key conflicts. A former owner who still has project read access can confirm an executed receipt but cannot create another update; removing all project access also removes that confirmation path. Posting does not send email/push or create project Inbox notifications; recipient-family integration remains explicitly pending.

## Drafts and permission changes

Status drafts start with empty new text. Closing retains a dirty draft and exposes Resume; workspace switching, unrelated follow-up creation and unload are guarded. A project/reference revision conflict retains typed text, refreshes the current audience/reference state, and requires renewed acknowledgement. An inaccessible/moved reference becomes an unavailable placeholder rather than silently changing the proposed report. A lost committed response retains frozen content and request identity for explicit retry.

Access refusal clears original project/history/reference details and retains only the user's new draft text and minimal project ID/version context. Text is exposed for readonly copying or explicit unsent-draft discard only after verifying the current account through the existing authenticated scoped workspace directory. A different/unknown account sees neither retained text nor enabled discard/post controls. Verification uses the existing identity, does not change credentials, and does not restore project permissions or replay automatically. Successful overview responses are also fenced to the original page viewer. Verification/draft continuations reject stale or replaced drafts.

Drafts remain page-memory only. If the original account cannot be verified (including loss of workspace/module eligibility), the draft remains hidden/sealed. Durable encrypted keep/logout/restart recovery, session restoration and pending-write reconciliation after credential loss are not accepted here; original identity/access restoration and the existing recovery gates are required. The corrected native preservation patch is unchanged, its write/recovery flags stay off, and the withdrawn automatic-purge behavior is not revived. Explicit draft discard does not remove posted history, source work or user files.
