# Projects, incoming tickets and guided work

Projects uses a full-width table with current department/person/status filters and sortable columns. New job creates a native project, incoming record and assigned task in one transaction. Create project starts an empty project. Incoming tickets defaults to unassigned submitted/triaged work. New ticket submits independently of a project; the reviewed department's current building choices and intake permissions apply. Move & assign reviews destination department, project, person and building before the explicit save. Assigned/complete views remain available; changing a view never moves records.

The browser combines only successful current permitted-department reads. It retains each response's department boundary for calendar/map projections: a saved building ID, current version and exact official source must match within that same response. A label, coordinate, another permitted department's building or stale version cannot establish a marker. Failed reads are excluded and reported. Counts describe returned data, bounded by100requests and200readable tasks per department; no all-campus access or hidden counts are inferred.

The native management adapter reuses WorkGraph and RequestWorkflow under the existing tenant lock. Every save has an exact request receipt and optimistic versions. Incoming routing requires current coordination of both departments and an existing active eligible assignee; it grants no membership. Project edits/archive require native ownership. Linked-task editing includes the current authorized request stamp even beyond the100-request list; incomplete/multiple/unreadable links require native review. Tasks with multiple actual memberships require native review even when one membership is private. Completed work retains existing operational controls. Remove task uses the existing soft deletion and retains stored records, files and history; it is not completion or a promised restore flow. Project archive is reversible. These controls create no account or provider activity.

Close/Escape retains existing discussion/progress drafts and list state. The job wizard retains its unsent form while closed in this tab. An uncertain write freezes the intended body for exact retry; a definitive rejection requires review/correction. Native Center/Side toggles keep one dialog/composer/file input. Roll Call project links return to the originating overview; changing department reauthorizes it. Workspace layout and service-intake preferences are reachable only inside Settings, never expanded in a work view. The compact heading keeps existing heading/breadcrumb tour anchors. Play at the three-minute end replays the tour from Scene1; replay itself changes no record.

The separate browser-only fictional upgrade `campus-jobs-20-v1` adds18stable project identities to the original2:20projects/jobs and21tasks because the original event project already has2tasks. It supplies10fieldworkers plus the Blaine demo-manager persona,5fictional contractors and5separate incoming tickets. It adds explicit same-area saved-building/version/source references and contractor schedules. The once-only marker preserves prior edits, notes, uploads, workflows and extra user-created work; removal tombstones are not resurrected. This is not a native SQL seed or a real Blaine account/grant. Browser storage failure is disclosed; providers and messages remain off.

Normal CI registers the native management test, sample migration/command/scope tests, separate native job-wizard scenarios and the actual Blaine browser flow in Chromium/WebKit. Local phone/iPad/720px reflow checks are viewport simulations, not physical-device acceptance. A release changes campus source fingerprint and needs the exact approved merged build, renewed publication binding and hosted persistence/isolation acceptance. Source preparation does not deploy or publish a version.

Blaine uses the explicit `demo_manager` browser persona. The separate Executive perspective remains read-only, including direct commands and receipt replay. The trusted default migrates the former Blaine/Executive choice once without replacing records, notes, uploads or later explicit role choices. Demo manager writes remain confined to the listed work controls; other Executive ancillary capability restrictions remain unchanged. No real account, membership or permission is granted.
