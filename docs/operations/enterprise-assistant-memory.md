# Explicit typed private memory (disabled source candidate)

`ENTERPRISE_ASSISTANT_MEMORY_ENABLED=false` and `ENTERPRISE_ASSISTANT_MEMORY_RETENTION_READY=false` independently gate this milestone. They do not enable a provider, trial, account, model, voice, send, business write or background schedule. Keep both off until this source is independently reviewed and a separately approved bounded cleanup job is installed and verified in the exact managed runtime. No cleanup schedule or production command is executed by this change.

Memory is private to the current account, tenant/silo and department. An owner/admin cannot inspect another account's entries. Current `WorkspaceAccess` applies to every inspect, preview, save, use and deletion. Saving/editing requires current department write permission; erasing an owned entry needs current department read access and the existing Enterprise writes gate, including after financial permission or the memory feature is lost. The UI offers memory only in the separately gated existing Ask pane. Role preview cannot select another account or add authority.

There are only two memory types. Formatting preferences choose a fixed reply length (`brief`/`standard`) or date style (`iso`/`long`); these are preferences, not current facts. Source observations select one bounded typed field actually supplied by a currently authorized canonical request, project, task, saved building or cost. The server previews its current version/hash and captures the value itself after a separately confirmed save. Supported fields are status, supported priority, due date, integer amount in minor units, currency and estimate/recorded-cost basis, only where that source provides them. An estimate is never an approved budget. No arbitrary text, secret, chat history, provider key, URL, observed value, model, tool or privilege can be submitted as a saved fact. Chat never creates memory automatically.

At most twenty active entries per account/workspace may be saved. Confirmation, fresh request UUID and expected version are required under the existing tenant lock and memory row lock. Exact retries replay only the still-current accepted version; changed bodies, stale edits, reused unrelated receipts and deleted IDs conflict. Entry content is encrypted in `TeamOperationRecord::data`; its unencrypted title is generic. Content-free action/version/hash/ID receipts and audit remain. No migration or new connection/grant is introduced.

Each entry exposes its confirming account/time, scope, source reference/version where currently authorized, and explicit 1/7/30-day expiry. The server recomputes canonical source/access before inspection/use. If a source changes, the saved value is withheld and a fresh explicit preview is required to replace it. If access is lost, source reference/title/value are withheld; the private entry remains erasable. A source observation can be included in a model request only if that source already belongs to the selected authorized check. Memory cannot cause extra retrieval, expand tools, change deterministic calculations or supply an approved budget/staffing fact.

The user opts in for each conversation; memory starts off and resets on Clear, reload/navigation/context reset. Only up to eight available typed entries are included, with provenance/expiry and clickable observation sources shown in the reply evidence. Their current IDs/versions/values participate in the short-session stamp and are rechecked before dispatch, returned answer and replay. Edits, deletion, expiry, source change and ACL loss invalidate old short-session reuse. If deletion occurs after a provider completed, the reply is withheld but its known charge remains. Stop/navigation never refunds an uncertain outcome or sends it again.

Deletion scrubs the entry's saved value with an explicit second confirmation, preserving work and spend evidence. A previously dispatched provider request cannot be recalled; a pending encrypted short-session payload/result can still contain the selected memory until explicit Clear or the existing short-session cleanup (at most ten minutes of authorized access). Provider retention/account policy requires exact connection approval; `store:false` does not establish zero retention.

Expiry denies value access immediately, independently of cleanup. The bounded managed-runtime command `php apps/enterprise/artisan enterprise:assistant-memory-prune --limit=100` scrubs expired active entries and increments their content-free version/audit; maximum batch is 1000. It requires an existing ready ClientSilo and does not initialize markers/ledgers, delete work or remove spend receipts. A separate approved scheduler must run repeated bounded batches, with backlog/error monitoring and a verified cleanup interval recorded before `RETENTION_READY=true`. Physical backups/provider retention are governed separately and are not erased by this command. Retention and edits serialize on the same row: a winning renewal is not scrubbed by a waiting stale scan; a winning expiry cannot be resurrected by a waiting stale edit.

Local tests use fictional managed runtime fixtures, empty env placeholders and fake HTTP only. Independent real MySQL workers cover retention/renewal races in both lock orders. Node lifecycle tests cover explicit consent, exact uncertain retries, mismatched previews and late context responses. The shared authenticated Chromium/WebKit smoke covers save/edit/reload/inspect/delete, opt-in recovery, desktop/iPad/mobile/reflow geometry, matching tour and actual normal/forced light/dark selector painting. These are simulated model tests, not live OpenAI or two-way voice acceptance.
