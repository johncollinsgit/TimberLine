# Private saved assistant configuration (disabled source milestone)

`ENTERPRISE_SAVED_ASSISTANTS_ENABLED=false` is independent of the paid connection. The existing Ask pane exposes its editor only with the separate conversation UI rollout. Preparing a private assistant does not activate a model, initialize a trial marker/ledger, change a role or alter work records. Main retail assistant routes and tables remain unchanged.

A saved assistant has an explicit name, purpose, instructions and selected read checks: current work, saved building work, recorded costs/estimates. These are fixed server capabilities, not provider function tools. There is no model, account, key, custom endpoint, arbitrary tool, voice or send field. Current `WorkspaceAccess` and feature checks restrict every read/use; financial checks remain owner/admin only. Role preview cannot select another actor or expand these checks. Unavailable checks remain unavailable, and edits save only checked currently available capabilities.

Profiles are private to the current account, tenant/silo and department. Managing one requires current write permission in that department; viewing/using one requires current read permission. A tenant owner/admin does not gain access to another person's private profile. At most ten active profiles per account/workspace can be saved. Retention is explicitly until deletion, with current authorized access required for management; this is configuration, not persistent fact/preference memory.

Name, purpose and instructions live in encrypted `TeamOperationRecord::data`; its unencrypted title is generic. Current owner/time/scope provenance is server generated. Writes require explicit confirmation, a request UUID and expected version under the existing tenant serialization lock. An exact retry returns its unchanged accepted version; a later edit, mismatched request body, stale version or reused unrelated receipt conflicts. Deletion requires a second explicit confirmation and scrubs profile content, while content-free audit/action/version/hash/ID receipts remain. Deleted IDs cannot be reused to resurrect content.

Selecting a profile includes its current owned configuration as untrusted user preferences in the already bounded provider payload. Its ID/version/current permitted checks participate in the session source stamp and are rechecked before dispatch, returned answer and replay. Editing/deleting the profile invalidates old short-session recovery rather than treating old instructions as current. The provider still receives no executable tools and uses the approved fixed model/account/cost policy. Profile instructions cannot grant retrieval authority or change deterministic calculations.

No chat is automatically captured as profile configuration. The editor warns against secrets and the server rejects recognizable private-key/token/password patterns; this is not a guarantee that arbitrary prose can never contain a secret. A selected profile's purpose/instructions may be copied into an encrypted pending short-session payload for that explicit turn. Deleting the profile does not erase an already-dispatched provider request, short conversation or spend receipt; clear the conversation to remove its content, and retain the existing retention-cleanup requirement. Provider retention remains part of exact connection approval; `store:false` alone is not a zero-retention promise.

The same Ask editor, profile selector, confirmation, exact-retry states and tour use current workspace/user context. Opening or editing a profile prevents Send until configuration is closed or saved. Navigation/access reset clears private form content and fences late responses. The browser does not store profile drafts, purpose/instructions or new provider settings. Persistent typed preferences and source-bearing saved facts, inspect/edit/delete/retention and their current source/ACL rechecks remain a separate memory milestone. Two-way voice remains separate.

This is separate from the current deployed Operations release. Keep every paid flag off until exact connection/security approval, existing ledger/baseline evidence and the independent review/CI/release procedure pass. A later AI/UI integration must explicitly transition the published review edition and use the coordinated final main base; never deploy this old-base implementation branch directly.
