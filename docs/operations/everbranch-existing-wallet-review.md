# Existing rewards wallet review

This default-off foundation records a request and an owner's review. It does not link an account, move a wallet, create a verified identity attestation, or enable rewards redemption. A customer-app implementation exists in an isolated local checkout; it is not deployed. There is no staff queue, notification, or staff UI yet. The customer must share the reference with an administrator. Responses explicitly include `linked: false` and `finalization_available: false`.

For Modern Forestry, the customer reads the disclosure and explicitly confirms a review request. Every request and status lookup requires a fresh authenticated Shopify customer subject. The request reference is an opaque hash, scoped to the tenant, subject, runtime, and client request UUID. It expires after 24 hours. The customer sees only their own review status, not the selected wallet or reviewer details.

An assigned tenant owner or administrator uses the register-scoped review API for that reference and explicitly selects an existing canonical customer. The reviewer must attest independent control using the exact disclosure; a matching email, name, phone, or payment card is not sufficient. Encrypted append-only audit events record the subject, canonical profile, reviewer, register, evidence category, exact disclosures, and timestamps. Repeating the same request or decision is idempotent; a changed decision conflicts. Every evidence category is an owner's attestation, not an independently authenticated wallet session. An expired request cannot be renewed with its old UUID; a customer may explicitly start a new request with a new UUID.

Before any final claim can be made available, implement an enforceable subject/identity fence shared by Shopify import and provisioning writers, review and merge paths, and wallet authorization. Finalization must independently reauthenticate the customer, recheck merge state, review expiry, exact subject and approved profile, ownership evidence and conflicting source identities; atomically consume a one-use approval with a signed attestation; and reject ambiguity for review. Add a staff interface, abuse controls and an explicit approval/revocation lifecycle. Validate concurrently against disposable MySQL with fictional data and retain the independent rewards rollout gate. No processing should depend on matching contact details or silently merge profiles.
