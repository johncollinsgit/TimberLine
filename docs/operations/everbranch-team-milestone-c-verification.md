## Implemented local behavior

**Templates:** current project owners capture versioned task or project snapshots. Project/task templates live in existing project JSON and create records through the same `WorkGraph` commands and tenant-locked repository; no parallel task store or new schema exists. Snapshots preserve title/description/priority, section identity, inherited child structure and child order. Copying requires current member + source-project edit access, current source-object access, template/project versions and explicit snapshot review. The API preview removes source-task/section identifiers; the UI displays readable captured text. New project copies are private with only the creating owner's grant. Task copies stay in the source project. Source history/provenance remains unchanged; new records retain protected internal template provenance.

Capture is bounded to 20 templates/project, 20 sections, 50 task nodes, five parent edges and 500 KB/template. Restricted descendants or oversize captures fail atomically, never as a silent partial project. Duplicate section names resolve by identity. Source deletion/revocation hides snapshots and prevents new use; existing intentional copies remain independent work. Owner-controlled removal retains existing work/copies and private native revisions. Both composite commands and UI retries use stable identities/receipts. Assignment, dates, completion state, custom fields, comments, files, original history, dependency edges and recurrence are intentionally excluded from this snapshot slice; copies start incomplete. These omissions are shown before copying and remain advanced-template backlog.

**Recurrence:** an explicitly reviewed `task.recurrence` rule supports daily/weekly/monthly calendar periods (interval 1–12), IANA zone, an inclusive last due date and/or a total occurrence limit (1–1000). It uses the existing `WorkspaceWallTime` resolver for timed deadlines. Completion creates exactly one next incomplete canonical task; nothing runs because time merely passes. The next deadline advances from the previous deadline, so late completion can create overdue work. Monthly rules retain the original day and clamp short months. Editing dates resets that calendar anchor. Date-only deadlines retain their literal day. Timed rules require minute precision, years 2000–2099; clock gaps reject atomically for user review and overlaps require the selected reject/earlier/later policy.

Next occurrences retain operational description, priority, current eligible assignment, authorized project memberships and typed values. Comments/files, dependency edges and source history stay on the original. Root tasks only; recurring subtasks or a parent with children require stopping/reviewing recurrence first. Personal recurrence requires the unshared creator; project recurrence requires edit access to every source project and a currently verified assignee. Reopen/recomplete, differently keyed retries and deleted successors cannot fork or resurrect a series. Existing successor records remain independent when an old occurrence's rule is cleared. No weekday/yearly/business-day rules, catch-up worker or recurring child blueprint is claimed.

**Dependencies:** a canonical task stores directed blocker references. Editors may add/remove links to readable endpoints or clear unavailable links. Self/transitive cycles and cross-tenant endpoints are rejected, with bounded graph/edge traversal. Completion remains advisory rather than implicitly completing or blocking other tasks. Read/search/API projection removes inaccessible endpoint IDs/titles/status; unknown endpoints remain blocked until reviewed. Only completion of the final currently visible blocker creates an eligible recipient-authorized internal Inbox event. It references the dependent task, rechecks both endpoint permissions, and is replay-safe. No push/email/provider job is dispatched.

**UI and races:** actual responsive task details expose recurrence, dependency search/direction/removal, and owner task-template capture. Project settings capture templates; the shared dialog previews/copies/removes them. Source text stays intact when planning controls encounter unsaved edits. An old task's delayed attachment response cannot overwrite a newer planning editor; hydration now checks generation again after the asynchronous file boundary. Controls have text status, native labels/details/dialog behavior, touch-size actions and bounded widths. This is web UI plus the existing gated bearer transport, not a native Team renderer or device acceptance.
