# Everbranch Team: discovery feature matrix

Date: 2026-10-11. Phase: discovery only. Repository inspected: `everbranch-team/app`.

This is a public technical code inventory and proposed acceptance scope, not an implementation or migration completion claim. The restricted coordinator report is authoritative for actual source counts, account/plan details, trial timing and private preview results; those operational details are intentionally absent here. No Team schema, application code, source data, browser state, production configuration, or deployment was changed by this audit. Existing files establish reusable foundations; running behavior and production availability are unverified unless explicitly stated below.

## Evidence and priorities

Discovery indicates private projects, populated project descriptions, archived work, event-oriented organization and familiar list/calendar navigation. These abstract patterns prioritize project lists, calendar/event work, historical preservation and privacy; a sidebar icon alone does not prove which view people actually use most often. Workspace scope, account identities, inventory, plan restrictions and timing must be verified in the restricted coordinator report. A trial countdown does not establish data deletion or the exact post-trial access policy.

Connector and browser identities can have different access. Accessible counts are scoped to an identity and collection method, not proof of a full company inventory; task memberships are not unique-task or complete-preservation counts. Missing roster pagination cannot establish a complete active/guest/former roster. Stories, recursive subtasks, attachment bytes and other source families require independent coverage evidence. This agent did not operate the browser or connector. Dependencies, rules, recurrence, forms, templates, guest access, mentions and board usage require source evidence before claiming actual usage or parity.

A representative private project contains older project notes alongside a much newer follow-up task, according to coordinator inspection. Do not collapse those into one inferred current date/contact. Exact names, dates, contacts and source passages belong only in the restricted evidence. The concrete vertical-slice plan and required fixtures are in `everbranch-team-ui-slice-plan.md`.

Orientation: `AGENTS.md`, `SYSTEM_SNAPSHOT.md`, and `README_FOR_AGENTS.md`. Newer October Field access notes supersede older assignment-only descriptions. Field Service jobs currently allow shared operational access for entitled active members, which is unsuitable as the default visibility rule for imported private Asana projects.

## Architecture implications before the vertical slice

Team should be a purchasable, tenant-scoped Branch using canonical catalog/access/billing services. Labels, enabled views, field mappings and source project selection are tenant configuration. Temporary pilot rollout selection belongs in configuration/provisioning, not runtime tenant-name branches. This is a recommendation for coordinator approval, not a new commercial declaration.

Do not convert Asana projects into Field Service jobs or reuse the client implementation portal by default. Existing Field scopes cannot preserve private project permissions, and its task foreign key does not support one generic task with multiple project memberships. Reuse authentication, tenancy, shell, storage/audit conventions, notification infrastructure, OAuth patterns and billing services through explicit Team contracts.

The first project slice should prove original notes/comments, private membership, list/sections, assignment/dates, task panel, search, source mapping, attachment bytes and resumability before adding broader views. Pick a representative accessible project only after source evidence shows its privacy and complexity. Treat board/calendar priority as a decision informed by actual project use, not a claim that inspection has proved all requested parity.

## Concrete next test setup and acceptance gaps

Use the locked dependencies in a disposable local/staging checkout, not production. Run `composer install` and `npm ci`, use a dedicated testing environment and writable compiled-view directory, then build assets. Do not use `composer setup` for an audit: its script generates a key and migrates the configured application database. Existing CI supplies the correct PHP/Node versions and Linux browser environment.

Before Team schema exists, useful regression baselines are `tests/Feature/FieldService/FieldServiceWorkspaceTest.php`, `tests/Feature/ClientProjects/ProjectChecklistTest.php`, `tests/Feature/ClientProjects/ClientProjectPortalTest.php`, `tests/Feature/Search/GlobalSearchControllerTest.php`, `tests/Feature/Onboarding/FirstLoginWorkspaceTest.php`, `tests/Feature/Billing/StripeCommercialFulfillmentTest.php`, and `tests/Feature/Mobile/TeamMessageAttachmentTest.php`.
